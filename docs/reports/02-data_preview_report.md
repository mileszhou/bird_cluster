# Data preview / audit report

Generated by `tools/audit_dataset.py` over `data`. Read-only; the dataset is not
modified. Re-run any time to refresh -- it takes ~15s over 35k sidecars.

## Layout assumed

```
<data-dir>/xmp/result-<YYYY>/bird_identification_output.csv
<data-dir>/xmp/result-<YYYY>/raw/<half-year>/<trip>/*.xmp
<data-dir>/jpg/<half-year>/*.jpg          # flat, no trip nesting
```

A sidecar's JPEG is looked up in the jpg folder whose name equals the sidecar's
half-year folder -- `raw/2023.1/<trip>/_X.xmp` -> `jpg/2023.1/_X.jpg`. Category and
species come from the sidecar's own `dc:subject` keywords (`code/lib/xmp_labels.py`),
never from the CSV: the CSV's `filename` column is a bare basename with no folder, and
basenames repeat within a year, so a basename-keyed lookup silently mixes up rows.
Measured duplicate basenames per year's CSV: 2018=180, 2019=76, 2021=429, 2023=2,
2024=347, 2025=484 -- and of those, 89 / 4 / 81 / 0 / 153 / 119 respectively have
duplicates that *disagree* on category.

## Unresolved bird sidecars, by half-year folder

Grouped by the folder that *should* have held the JPEG; only folders with at least one
unresolved sidecar are listed. Two very different failures live here:

- **`cross-yr`** -- exactly one JPEG with that stem exists, in a *different year*. This
  is camera counter wraparound: the same frame number reused years apart. A matcher that
  falls back to a whole-tree stem lookup returns **a photo from an unrelated shoot**,
  with no error. This is the class that has to be refused.
- **`+same-yr`** -- the only JPEG is in an adjacent folder *within the same year*, i.e.
  the export split fell in a different place than the sidecar split. Same shoot, right
  photo; safe to accept.

guesses, so the tail is partly genuine rarity and partly noise. A density-based

the shape of the data, not a failure of the method.
